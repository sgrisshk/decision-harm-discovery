## 1. What runs, exactly

The real, unmodified `discover_candidates()` from the frozen engine
(`discovery-engine-v0.6.2`, `packages/analytics/src/policy_analytics/discovery/engine.py`,
sha256 `fefceeaac20e8ff7b57f4e7a9cc9a1e9c649dd05269e10884d358d326d2e4549`, validation contract
**1.3.0**, no `G17`) — **not** the atom-grid builder (`_atoms`), **not** `build_projection`, and
**not** any oracle stand-in used in `TASK-107` Phases 1-2c. This is the first and only time this
function is ever called against benchmark v2's composite generator in this benchmark's history.

`DiscoveryConfig()` is used at its frozen defaults for every field. The only field given a
non-default value is `seed`, set to the draw's own seed for run provenance only — confirmed by
direct inspection (`grep '\.seed\b' engine.py` returns no hits) that `DiscoveryConfig.seed` is
never read by any search/ranking/selection logic inside `engine.py`; it has no effect on the
search's actual behavior and recording it is not a parameter change. This exactly follows the
existing convention in `scripts/run_discovery.py` (`DiscoveryConfig(seed=int(manifest["random_seed"]))`)
and `scripts/diagnose_task106_fn_autopsy.py`'s own real-engine path.

Candidates are graded by the real, unmodified `run_validation()` (contract 1.3.0,
`packages/analytics/src/policy_analytics/validation/contract.py`,
sha256 `a55fdc94c7e520cc4e287c6627d345e5a2335bfc1bd684db584218790b7403cd`), using the multiplicity
family size the engine's own search actually reports for that seed
(`discover_candidates(...)["search"]["evaluated_hypotheses"]`) — **not** the fixed 60,000
"primary" placeholder the freeze manifest records for the oracle-only acceptance runs (that number
was explicitly "independent of any engine output," i.e. a stand-in for a run that never exercised
the real search; it does not apply here). This matches the precedent already set by
`scripts/diagnose_task106_fn_autopsy.py`'s own real-`discover_candidates` path, which uses
`doc["search"]["evaluated_hypotheses"]` as the family size, never a fixed oracle number, whenever
the real engine is actually run. Scored with the real, unmodified
`benchmark_v2_scoring.py` (sha256 `0878811a737ad3608f2ee14568f10a67fc92fd052d866c261d44c9650a8ada1b`):
Coverage/Specific/Exact definitions, vacuity, trap exemption — none redefined, none retuned.

The composite dataset for each seed is generated by the real, unmodified
`synthetic_benchmark_v2.generate_v2` with **all 20** `TargetDesign` records
(`synthetic_benchmark_v2_targets.DESIGNS`, sha256
`4a9e75a8d27284dbaa20ba0467d43871d0df20db6e16268ca01af208eb9d2059`) dosed together, additively, on
the same rows — the frozen dense composite, exactly as `TASK-107` built it. Reused unmodified:
`docs/benchmark/task-107-evidence/v2_common.py`'s `build_draw()` helper (same dataset-construction
call sequence as Phases 2b/2c).

## 3. Ground truth used for scoring — scope decision, disclosed before any run

Per `TASK-109`'s binding scope ("Headline denominator = the 11 Core targets only... `D01`...
reported separately"), this run constructs `benchmark_v2_scoring.Target` records for exactly:

* **The 11 final Core targets** (`C02, C04, C06, C07, C08, C09, C11, C12, C14, C15, H01`),
  `stratum="core"`, `assessed=True`.
* **The 3 Core-FAIL targets** (`C01, C10, C13`) — included so they appear in the "core" stratum's
  `unscoreable` accounting for transparency, but with `assessed=False`, which (per `ADR-108`
  Decision 3 — an existing scorer mechanism, not a new one introduced by this task) makes them
  permanently uncreditable and ineligible for any trap exemption, matching the freeze manifest's
  instruction that they are "permanently recorded as Core-FAIL," not Core, not redesigned, not
  silently dropped.
* **`D01`** (the sole `oracle_qualified` `DECLARED_OVERLAP` target), `stratum="declared_overlap"`,
  `assessed=True`, reported separately and never mixed into the Core denominator.
* **The five trap literals `T01-T05`** (`docs/benchmark/task-107-evidence/v2_common.TRAP_LITERALS`,
  unmodified), for the scorer's existing safety/trap-exemption machinery.

**Challenge-only designs (`C03, C05, H02, H03`) and the non-qualifying `D02` are not constructed as
targets at all** — they are out of `TASK-109`'s scope (the binding text names only the 11 Core
plus `D01`), and are not needed for correct scoring: none of their trap literals bear on the 11
Core + `D01` set (checked directly against `synthetic_benchmark_v2_targets.DESIGNS`), so omitting
them changes no number this task reports. This is a scope choice by the implementer, flagged here
explicitly as required by `TASK-109`, not a silent scorer default — the composite dataset itself
still contains all 20 targets' effects, dosed together; only the *scored* target set is narrowed.

`canonical_in_language` for every included target is its own conditions unchanged (every one has
<= 3 conditions and no `in`-operator clause, so it is already in-language — same default rule
`evaluate_benchmark_v2.py` applies when a pattern doesn't declare a different canonical form).

## 4. Expected output schema

For **each of the 30 seeds** (raw, committed under `docs/benchmark/task-109-evidence/engine-raw/`):

* `seed`, frozen-version record (engine sha256 prefix, contract version, `g17_present`).
* The engine's raw output: candidate count, every candidate's conditions, development metrics,
  `rank_score`, warnings (`discover_candidates()`'s own return value, unmodified).
* The family size actually used for validation (`evaluated_hypotheses`, engine-reported).
* Per-candidate validation: `evidence_level`, `policy_readiness`, `verdict`, failed gates.
* The real `benchmark_v2_scoring.score()` output for that seed: per-stratum `scoreable`,
  `unscoreable`, `coverage_targets`, `specific_targets` (at `theta_J=0.50` and the sensitivity
  thetas the scorer already computes), `exact_targets`, `exact_after_vacuity_targets`,
  `exact_defined_targets`, plus the `safety` block (trap hits/promotions/provenance) and the
  per-candidate records (`per_target` metrics, `credited_target`, `in_pool`, etc.) — nothing
  beyond what `score()` itself already returns.

**Aggregated** (`docs/benchmark/task-109-evidence/engine-aggregate-rates.json` plus the results
document):

* For the 11 Core targets and separately for `D01`: a per-target `k/30` rate for Coverage,
  Specific (headline, `theta_J=0.50`), and Exact — the number of the 30 seeds on which that target
  individually reached each bar (mirroring the `k/30`-per-target style every prior `TASK-107`
  phase already used for its own acceptance/calibration/C5 rates).
* The funnel per target, at minimum: generated candidate count (per seed, and summed/listed across
  seeds) -> Coverage -> Specific -> `predictive_association`, plus whatever finer decomposition
  `score()` already returns (e.g. `specific_metric_also_holds_for`, `exact_after_vacuity`,
  vacuity-dropped conditions) — introducing no new funnel stage.
* The **aggregate headline** stated as "`X`/11 Core targets reached [Coverage/Specific/Exact] on
  at least 1 of the 30 seeds" — this is the implementer's own chosen aggregation method for
  turning 30 per-seed, per-target outcomes into one project-level number, disclosed here, before
  any run, as a methodological choice for the reviewer to weigh (not silently picked afterward for
  favorable framing): a one-shot "ever discovered across 30 independent composite draws" bar,
  distinct from (and not comparable to) `TASK-107`'s own `>=0.90` Clopper-Pearson-lower-bound,
  30/30-style oracle-qualification bar, which answered a different question (whether the *true
  rule* is detectable at all) under an ADR-fixed statistical standard. Both the per-target `k/30`
  table and this aggregate are reported together; neither is presented without the other.
* `D01`'s own Coverage/Specific/Exact `k/30` rates and funnel, reported in its own block, labeled
  `DECLARED_OVERLAP`, never summed into or compared against the 11-target Core aggregate.
